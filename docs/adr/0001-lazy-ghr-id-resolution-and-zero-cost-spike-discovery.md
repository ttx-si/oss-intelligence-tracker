# Lazy GitHub Repo ID Resolution, Secondary Rate-Limit Pacing, and Fault-Isolated Spike Discovery

Trending HTML pages (`gtrending`) and curated markdown issues (`HelloGitHub`) only expose mutable `owner/repo` paths and are prone to upstream DOM/formatting changes, while `Trendshift Signal API` requires a paid subscription. We decided to combine multi-language daily and weekly `gtrending` boards (normalizing 7-day weekly `currentPeriodStars` to a 24-hour daily rate while preserving daily deltas on deduplication), GitHub's native Search API across 7-day (`stars:>=50`, `per_page=100`) and 30-day (`stars:>=200`, `per_page=100`) breakout windows (normalizing cumulative stars by repository age in days so first-observation Cold Start evaluation uses a true daily velocity), two-stage `HelloGitHub` issue discovery (`/content/HelloGitHub{num}.md` index resolution plus direct and click-redirect link parsing), and `OSSInsight` (raising on `data_quality.status == "unavailable"` so upstream deprecation surfaces through the circuit breaker) as our default zero-cost Signal Sources (keeping Trendshift as an opt-in adapter gated by `TRENDSHIFT_API_KEY`). Every signal adapter runs in an isolated circuit breaker so a single broken scraper logs a structured warning without aborting the pipeline. Known `owner/repo` paths are matched case-insensitively (`COLLATE NOCASE`) in SQLite, while unknown `owner/repo` strings lazily resolve immutable integer `ghr_id` values via `GET /repos/{owner}/{repo}` with a 100–200ms jittered pacing delay between requests to prevent GitHub Secondary Rate Limit (`403`) bans during cold-start bursts, updating `full_name` in place whenever a resolved `ghr_id` matches an existing renamed repository.
