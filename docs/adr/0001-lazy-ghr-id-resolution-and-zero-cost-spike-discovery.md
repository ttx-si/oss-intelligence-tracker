# Lazy GitHub Repo ID Resolution, Secondary Rate-Limit Pacing, and Fault-Isolated Spike Discovery

Trending HTML pages (`gtrending`) and curated markdown issues (`HelloGitHub`) only expose mutable `owner/repo` paths and are prone to upstream DOM/formatting changes, while `Trendshift Signal API` requires a paid subscription. We decided to use GitHub's native Search API (repositories created within the last 7 days with high star velocity) paired with local snapshot delta calculation as the default zero-cost spike detector (keeping Trendshift as an opt-in adapter gated by `TRENDSHIFT_API_KEY`), and to wrap every signal adapter in an isolated circuit breaker so a single broken scraper logs a warning without aborting the pipeline. Unknown `owner/repo` strings lazily resolve immutable integer `ghr_id` values via `GET /repos/{owner}/{repo}` with a 100–200ms jittered pacing delay between requests to prevent GitHub Secondary Rate Limit (`403`) bans during cold-start bursts, updating `full_name` in place whenever a resolved `ghr_id` matches an existing renamed repository.
