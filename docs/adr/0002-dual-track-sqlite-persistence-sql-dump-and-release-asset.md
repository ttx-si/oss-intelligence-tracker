# Dual-Track SQLite Persistence via Deterministic Ordered SQL Export and Rolling Release Asset

Committing a binary `intelligence.db` file every 6 hours bloats `.git` history to hundreds of megabytes, while default `sqlite3 .dump` output relies on internal `rowid` ordering that causes noisy Git diffs whenever rows are reorganized. We decided to enforce a global workflow concurrency lock (`group: db-pipeline, cancel-in-progress: false`), explicitly grant `permissions: contents: write` in GitHub Actions workflows, and split persistence into two tracks: Git commits a custom plain-text SQL export explicitly ordered by `ghr_id ASC` (and `ghr_id ASC, captured_at ASC, signal_source ASC` for snapshots) to guarantee minimal line-level diffs, while each run overwrites a compiled binary `intelligence.db` asset on a rolling GitHub Release tag (`latest-db`) for fast downstream consumption.

Both tracks are published only from the default branch. The runner pulls before installing the checked-out code, then atomically creates a durable recovery gate (`refs/heads/intelligence-recovery-pending`) via an absent-ref compare-and-swap lease before ingestion or notification delivery so any subsequent queued run stops fail-closed until both tracks finish publishing and the run deletes its own gate lease. On bounded publication retries (up to three), the runner enforces monotonic forward ancestry across fetches (preventing rollbacks or history rewrites from being undone even when `data/schema_data.sql` is unchanged), verifies SQL has not changed from the ingestion baseline, rebases unrelated updates, verifies fast-forward ancestry, and pushes with a compare-and-swap lease (`--force-with-lease=refs/heads/$GITHUB_REF_NAME:$remote_tip`) before uploading `latest-db`. Failed gated runs attempt to retain `intelligence.db`, `data/schema_data.sql`, and `intelligence-base-revision.txt` as a short-lived Actions artifact while keeping `refs/heads/intelligence-recovery-pending` active until a maintainer reconciles data and notification watermarks and deletes the gate ref (`git push origin :refs/heads/intelligence-recovery-pending`). Gate creation, notification delivery, Git push, Release upload, gate deletion, and artifact upload span separate operations and cannot form one atomic transaction: pre-delivery or post-push failures also hold the gate until cleared, runner termination or artifact-upload failure can lose unexported local watermarks, and deleting the gate before reconciling watermarks can permit duplicate notifications.
